# Annotator — Implementation Plan & Log

A small Rust TUI application for annotating code files. You open a file, "paint"
(select) a range of lines, write a review-style note, and the app saves the
annotation to a file named `<UUID>.md` containing the note plus metadata.

## Requirements

- Open a code file and view it in a terminal UI.
- Select ("paint") a range of lines, like a review comment.
- Write a free-text note about the selected lines.
- Save the annotation to `<UUID>.md` (UUID generated by the app).
- The saved file stores metadata in addition to the comment:
  - git commit hash (if available)
  - hash of the file contents
  - the file name
  - the lines in question (start–end range)

## Design decisions

- **UI**: Terminal UI (TUI) built with `ratatui` + `crossterm`. "Painting" lines
  maps naturally to a vim-like visual selection in the terminal.
- **Interaction model** (modal, vim-inspired), one TUI session for everything.
  The second header line always shows the main keys for the current mode
  (kept within 80 columns); `?` opens a help screen listing every key.
  - File view: `j`/`k` or arrows move, `g`/`G` top/bottom, `v` paint (select)
    lines, `c`/`Enter` comment the line(s), `f` comment the whole file,
    `b` open the file browser (in the open file's directory), `q` quit
  - Painting: move to extend, `c`/`Enter` comment the selection, `v`/`Esc` stop
  - File browser: `j`/`k` `g`/`G` move, `Enter` open file or directory,
    `l`/`→` enter directory, `h`/`←`/`Backspace` parent, `c` comment the
    selected file or directory, `C` comment the current directory, `Esc` back
    to the open file, `q` quit
  - Note editor: title says what is being commented on; `Esc` save, `Ctrl+Q`
    discard (back to where you were), `Enter` newline, `←`/`→` move; text
    word-wraps and the box grows up to half the screen, then scrolls
  - Mouse: the wheel scrolls the file or browser (the cursor is pulled along
    to stay on screen, so while painting it extends the selection); in the
    file view a click moves to a line and dragging with the left button paints
    lines (dragging past the top/bottom edge scrolls); in the browser a click
    selects an entry and clicking the selected entry opens it. Ignored while
    writing a comment. Mouse capture means terminal text selection needs the
    terminal's modifier (e.g. Shift, or Option in iTerm2)
  - `annotator` starts in the browser at the working directory,
    `annotator <file>` starts in the file view
- **Scopes**: an annotation is about a line range (TUI painting or
  `<file> --lines A-B`), a whole file (TUI `f` / browser `c`, or `--path FILE`)
  or a whole directory (browser `c`/`C`, or `--path DIR`). A directory gets one
  annotation, not one per file. Paths inside the working directory are stored
  relative to it.
- **Storage**: one Markdown file per annotation, named `<UUID>.md`, written to
  an `annotations/` directory in the current working directory (configurable via `--output-dir`).
- **Metadata**: collected at save time:
  - `git rev-parse HEAD` of the repo containing the file (optional, if in a repo)
  - SHA-256 of the *whole* file, also for line ranges, so a working tree that
    has drifted from `git_commit` can be detected
  - for directories: SHA-256 of a manifest with one `<sha256>  <relative path>`
    line per file, sorted by path — the same as
    `git ls-files -co --exclude-standard | sort | xargs sha256sum | sha256sum`.
    Inside a repo the file list is tracked + untracked-but-not-ignored files
    (so `target/` is skipped, deleted files are listed as `deleted`); outside a
    repo it is a recursive walk that skips hidden entries
  - scope: the path plus, for line annotations, the line range, as one
    code-link style reference — `src/` (directory, trailing slash),
    `src/foo.rs` (file), `src/foo.rs#L3-7` (lines, 1-based inclusive; a single
    line is `#L3`)
  - timestamp (UTC)
- **Output format** (`<UUID>.md`):

  ```markdown
  # Annotation

  - scope: `path/to/file.rs#L12-18`   (or: `path/to/file.rs`, `path/to/dir/`)
  - git_commit: <hash or "unavailable">
  - content_sha256: <hash>
  - created_at: <RFC3339 UTC>

  ## Context                (only for line ranges)

  ```rs                     (language tag = file extension)
  <the annotated lines>
  ```

  ## Comment

  <note text>
  ```

## Dependencies

- `ratatui` + `crossterm` — TUI
- `uuid` (v4) — annotation file names
- `sha2` — content hashing
- `chrono` — timestamps

## Testing

`cargo test` runs:

- `src/annotation.rs` — hashing, Markdown output (incl. the `Context` code block), git detection, file and
  directory annotations, `.gitignore`-aware directory hash.
- `src/app.rs` — syntax highlighting, comment wrapping (`wrap_note`), key
  handling for every action (painting, mouse wheel/click/drag, line/file/directory comments, discard,
  empty comments, browser navigation and switching files, help screen) and
  rendering into ratatui's `TestBackend` (comment box wrap/grow/scroll and
  cursor placement, key hints per mode and their 80-column limit, help screen
  lists every key).
- `tests/cli.rs` — runs the built binary in temp dirs and git repos: all
  metadata fields, dirty-tree detection, line-range clamping, `--path` for
  files and directories, and every argument/runtime error path.

## Feedback from User Testing

Issues and feature requests collected from annotation files in `annotations/`
(source annotation ID prefix in brackets).

### Open issues
- **Default output directory** [`e089cf26`]: the default (`annotations/` relative to where
  the tool is run) is not really visible. Requested: `<repository root>/annotations/` when inside
  a git repository; otherwise the working directory the tool was started from. To clarify:
  whether outside a repo that means the working directory itself or `<cwd>/annotations/`.
  (Related: the header shows `saves to: annotations`, a relative path, not the resolved
  location.)

### UX Improvements (Addressed)
- **Visual mode key** [`2792dba9`]: lowercase `v` starts/stops painting (`V` still works)
- **Line wrapping in the comment box** [`437fa259`]: the editor word-wraps, grows up to half
  the screen and then scrolls to keep the cursor visible
- **Output location visibility** [`9e367b20`]: Added `saves to: <output_dir>` in the header
- **Help text** [`9e367b20`]: Clarified "v paint multiple lines" in the header
- **Cancel comment** [`5b79496a`]: Added `Ctrl+Q` in editing mode to discard a comment without saving
  (requested as a special `/exit` command; `Ctrl+Q` chosen as more idiomatic for a TUI)
- **Syntax highlighting** [`9e367b20`]: Added basic Rust syntax coloring for keywords (fn, let, pub, etc.), strings, and comments (line and block)

### Feature Requests (Addressed)
- **One unified scope** [`64bca40a`]: `scope`, `file`/`path` and `lines` were redundant; now a
  single `- scope:` field holds `src/`, `src/foo.rs` or `src/foo.rs#L3-7` (GitLab-style range,
  as suggested; a single line is `#L3`). Older annotation files keep the previous fields
- **Copy the painted lines into the annotation** [`998108af`]: line annotations (TUI and
  `--lines`) get a `## Context` section with the lines in a code block, before `## Comment`;
  the fence is lengthened when the code itself contains backtick runs
- **Mouse support** [`38f00d92`]: the wheel scrolls, click moves to a line, left-drag paints
  lines; in the browser click selects and a second click opens
- **Support commenting entire directories or paths** [`6e12dd0d`]: `--path FILE|DIR --note TEXT`
  writes a single annotation for the whole file or directory; an empty note is rejected
  (the earlier version wrote one empty annotation per file: `03fb2d0f`, `4ef8b1af`, `a879f431`)
- **Hash scope** [`41ee6bdc`, `6e12dd0d`]: `--hash-scope` removed; file and line annotations
  always hash the whole file, directories hash a manifest of their files (see Design decisions)
- **Built-in file selection/navigation** [`b3ef44ab`]: Implemented file browser mode in TUI with
  `j/k` navigation, `Enter` to select, `h/Left` to go to parent
- **Comment whole files from the TUI** [`8b628f99`]: `f` in the file view (the annotation
  suggested `w`), or `c` on a file in the browser
- **All actions available in the UI** (user feedback, not an annotation): the browser was only
  reachable by starting without a file and its keys were not shown. Now `b` opens it from any
  file, `Esc` returns, whole-file and directory comments work from the TUI, each mode shows its
  keys and `?` lists them all
